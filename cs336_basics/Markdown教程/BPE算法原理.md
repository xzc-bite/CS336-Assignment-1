## 1. 为什么需要 Tokenizer

### 1.1 文本到数字的桥梁

自然语言处理模型的输入只能是**数值**（整数或浮点数向量），而原始文本是离散的符号序列。Tokenizer（分词器）的核心职责就是在"文本字符串"与"整数序列"之间建立双向映射：

```text
文本 "hello world"  →  Tokenizer  →  [15496, 995]  →  模型
```

这个映射关系存储在**词表（Vocabulary）**中：词表是一张"Token 字符串 ↔ 整数 ID"的对照表，分词就是查表过程，解码就是逆过程。

### 1.2 三种分词粒度的问题

如何切分文本，直接决定词表大小与模型的表示能力。常见的三种粒度各有明显缺陷：

| 粒度 | 示例 | 问题 |
| --- | --- | --- |
| 字符级（char-level） | `"unbelievable"` → `u n b e l i e v a b l e` | 词表极小，但序列过长；单个字符几乎不含语义，模型难以学习"unbelievable"这样的整体概念，训练和推理开销大 |
| 单词级（word-level） | `"unbelievable"` → `["unbelievable"]` | 语义完整，但词表随语料无限膨胀；遇到未登录词（Out-of-Vocabulary, OOV）只能映射为 `<unk>`，信息全部丢失；词嵌入矩阵巨大，稀疏训练不充分 |
| 子词级（subword） | `"unbelievable"` → `["un", "believ", "able"]` | 兼顾两者：常用词保持完整，罕见词拆分为有意义的子词，OOV 问题大幅缓解 |

**子词分词（Subword Tokenization）** 是现代 NLP 的主流方案，而 BPE 是其中最经典、应用最广的算法之一（GPT-2、GPT-3/4、RoBERTa、LLaMA 等均使用 BPE 或其变体）。

### 1.3 Tokenizer 在 NLP 中的作用

1. **离散化**：把连续文本转为离散符号，再映射为模型可计算的整数 ID。
2. **控制序列长度**：相比字符级，子词能显著缩短序列，降低注意力机制的平方级开销。
3. **平衡词表规模与语义粒度**：词表大小通常控制在 3 万 ~ 20 万之间。
4. **处理多语言与罕见词**：任何单词都可以拆成已知子词的组合，跨语言迁移更容易。
5. **影响模型效果**：词表的构建方式（词表大小、语言覆盖、预处理规则）会直接影响模型的困惑度、生成质量和推理成本。

### 1.4 常见分词方法概览

- **BPE（Byte Pair Encoding）**：数据驱动的贪心合并算法，本文主题。
- **WordPiece**：与 BPE 类似，但按"合并后语言模型似然提升最大"而非纯频率选择合并对（BERT 使用）。
- **Unigram（SentencePiece）**：从较大词表出发，逐步删除对似然贡献最小的子词（ALBERT、T5、LLaMA 使用）。
- **Byte-level BPE**：以字节（而非 Unicode 字符）为初始词表，从根本上消除 OOV（GPT-2 及之后的大多数模型）。

## 2. BPE 的基本定义与核心思想

### 2.1 从数据压缩到 NLP

BPE 最初是一种**数据压缩算法**（Philip Gage, 1994）：通过反复把数据中出现频率最高的字节对替换为一个新字节，来缩减数据体积。2015 年，Sennrich 等人在论文 *Neural Machine Translation of Rare Words with Subword Units* 中将其引入 NLP 领域，用同样的思想构建子词词表——把高频字符对合并成"子词"，从此 BPE 成为神经机器翻译及后续大语言模型的标准分词方案。

### 2.2 BPE 的定义

**BPE 是一种数据驱动的子词分词算法：从单个字符（或字节）出发，迭代地在训练语料中找出出现频率最高的相邻符号对，将其合并为一个新符号并加入词表，直到达到预设的词表大小或没有可合并的符号对。**

训练产物是一张**有序的合并规则表（merge list）**，分词（编码）时按规则表的顺序对文本反复应用合并，即可得到子词序列。

### 2.3 核心思想

1. **频率驱动**：语料中出现越频繁的相邻符号，越值得被合并为一个独立 Token。这样高频模式（如英文中的 `ing`、`tion`）会被合并成完整子词，而低频组合保持拆分状态。
2. **从细到粗的贪心构建**：词表不是人工设计的，而是从字符级开始"自动生长"出来的——每一轮合并只新增一个 Token，词表规模可控。
3. **开放词表（Open Vocabulary）**：任何输入文本都能被切分为已有子词的组合，从根本上缓解 OOV 问题。
4. **压缩与表示的折中**：常用词切分出较少的 Token（序列短、语义完整），罕见词切分出较多的 Token（序列长、信息不丢失）。

### 2.4 BPE 的特点小结

- 训练过程**无监督**，只需要原始文本，不需要词性、词典等标注；
- 训练与推理都很快，规则表就是全部"模型参数"；
- 词表大小由"合并轮数"直接控制，可精确调节；
- 是贪心算法，不保证全局最优，但实践效果与效率俱佳。

## 3. 预分词（Pre-tokenization）

### 3.1 什么是预分词

在执行 BPE 训练（以及后续的分词）之前，通常先用一套简单规则把原始文本切分为若干个**词（word）**大小的块，这一步称为**预分词（Pre-tokenization）**。

BPE 的合并统计只在**单个词内部**进行，**不允许跨词合并**。例如文本 `"lower newest"` 会先被切成 `["lower", "newest"]` 两个词，然后分别对每个词做字符级拆分与合并，绝不会把跨词边界的相邻符号合并成一个 Token。

### 3.2 常见预分词规则

不同模型采用不同规则，典型代表：

- **按空白与标点切分**：最朴素的规则，`"Hello, world!"` → `["Hello", ",", "world", "!"]`。
- **GPT-2 的正则规则**：用一条正则表达式完成预分词，把字母、数字、标点、空白分别成组，并处理英文缩略形式：

  ```text
  's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
  ```

  注意 ` ?\p{L}+` 中的**前导空格被保留在词内部**——空格不是独立 Token，而是附着在下一个词的开头（在词表中记作 `Ġ`，如 `" world"` 对应完整 Token `Ġworld`）。

- **SentencePiece**：直接把文本中的空格也当作普通字符处理（用 `▁` 表示），先做归一化再做切分，对中日韩等无空格语言更友好。

### 3.3 预分词对 BPE 流程的影响

1. **限定合并范围**：合并不会跨越词边界，避免了把两个不同词的局部错误地粘成一个 Token。
2. **保留边界信息**：空格、标点等"结构信息"以词内符号的形式进入词表，解码时可以完整还原文本。
3. **决定词内符号序列的形态**：`"world"` 在 GPT-2 中实际参与训练的序列是 `Ġ w o r l d`，而不是 `w o r l d`——前导空格参与了后续所有合并。
4. **影响训练统计口径**：频率统计以"词"为单位聚合，同一个词在语料中出现多少次，其内部所有符号对的计数就加权多少次。
5. **影响最终切分行为**：分词时同样要先做预分词，再在词内应用合并规则；预分词规则不同的两个模型，即使词表相同，切分结果也可能不同。

## 4. BPE 训练步骤详解

### 4.0 训练语料示例

下面用一个经典的小型语料，完整演示 BPE 的每一轮迭代：

| 词 | 频率 |
| --- | --- |
| `hug` | 10 |
| `pug` | 5 |
| `pun` | 12 |
| `bun` | 6 |
| `hugs` | 3 |
| `pugs` | 2 |
| `punk` | 4 |

### 4.1 步骤一：构建初始词表

把每个词拆成**字符序列**，所有出现过的字符构成初始词表：

```text
hug  → h u g
pug  → p u g
pun  → p u n
bun  → b u n
hugs → h u g s
pugs → p u g s
punk → p u n k
```

初始词表（8 个符号）：`h, u, g, p, n, b, s, k`

> 若采用 byte-level BPE，则初始词表固定为全部 256 个字节值，与语料无关。

### 4.2 步骤二：统计相邻符号对频率

遍历每个词的符号序列，统计所有**相邻符号对**的出现次数，并按词频加权累加。第一轮的统计结果为：

| 符号对 | 计数 | 来源 |
| --- | --- | --- |
| `(p, u)` | 23 | pug(5) + pun(12) + pugs(2) + punk(4) |
| `(u, n)` | 22 | pun(12) + bun(6) + punk(4) |
| `(u, g)` | 20 | hug(10) + pug(5) + hugs(3) + pugs(2) |
| `(h, u)` | 13 | hug(10) + hugs(3) |
| `(b, u)` | 6 | bun(6) |
| `(g, s)` | 5 | hugs(3) + pugs(2) |
| `(n, k)` | 4 | punk(4) |

### 4.3 步骤三：选择最高频对执行合并

选出计数最高的符号对 `(p, u)`（计数 23），将其合并为新符号 `pu`，并**全局替换**所有出现位置：

```text
pug  → pu g
pun  → pu n
pugs → pu g s
punk → pu n k
```

### 4.4 步骤四：更新词表并迭代

把新符号 `pu` 加入词表（词表规模 8 → 9），然后重复步骤 2 ~ 4，直到达到预设词表大小（或合并次数）为止。

完整的前 4 轮迭代如下：

| 轮次 | 最高频符号对（计数） | 合并结果 | 合并后的语料 |
| --- | --- | --- | --- |
| 初始 | — | — | `h u g` / `p u g` / `p u n` / `b u n` / `h u g s` / `p u g s` / `p u n k` |
| 1 | `(p, u)` → 23 | `pu` | `h u g` / `pu g` / `pu n` / `b u n` / `h u g s` / `pu g s` / `pu n k` |
| 2 | `(u, g)` → 20 | `ug` | `h ug` / `pu g` / `pu n` / `b u n` / `h ug s` / `pu g s` / `pu n k` |
| 3 | `(pu, n)` → 16 | `pun` | `h ug` / `pu g` / `pun` / `b u n` / `h ug s` / `pu g s` / `pun k` |
| 4 | `(h, ug)` → 13 | `hug` | `hug` / `pu g` / `pun` / `b u n` / `hug s` / `pu g s` / `pun k` |

可以看到：高频模式（`pu`、`ug`、`pun`、`hug`）逐渐长成完整子词，而低频组合（如 `(g, s)`、`(n, k)`）排在后面处理，甚至可能因达到词表上限而永远不被合并。

### 4.5 训练产物：合并规则表

训练结束时得到两张表：

1. **词表（vocab）**：所有 Token 字符串到 ID 的映射（初始符号 + 全部合并产物 + 特殊 Token）。
2. **合并规则表（merges）**：按学习顺序排列的符号对列表，例如：

   ```text
   p u
   u g
   pu n
   h ug
   ...
   ```

   这张**有序**规则表就是 BPE 的"模型"，编码时按顺序应用。

### 4.6 小项目：亲手走一遍编码与解码

#### 任务背景

训练结束后，我们手上只有两张表：一张**词表**（Token 字符串 ↔ ID），一张**有序的合并规则表**。从这一刻起，它们就是分词模型的全部。本节的任务是：拿这两张表，把一句新文本切成 Token，再把 Token 还原成文本。

动手过程中重点回答两个问题：

- 为什么同样一句话，不同模型切出的子词不一样？
- 规则表里的"先后顺序"到底起什么作用？

#### 第一步：认识我们的模型（规则表与优先级）

把 4.1 节的训练语料学满 10 轮，得到下面这张规则表。**顺序就是优先级，排在前面的先执行**：

```text
第 1 条   p  u   → pu
第 2 条   u  g   → ug
第 3 条   pu n   → pun
第 4 条   h  ug  → hug
第 5 条   pu g   → pug
第 6 条   b  u   → bu
第 7 条   bu n   → bun
第 8 条   pun k  → punk
第 9 条   hug s  → hugs
第 10 条  g  s   → gs
```

配套词表（ID 按创建顺序编号）：

```text
0:h   1:u   2:g   3:p   4:n   5:b   6:s   7:k      ← 初始字符
8:pu  9:ug  10:pun  11:hug  12:pug  13:bu  14:bun  15:punk  16:hugs  17:gs   ← 合并产物
```

注意规则表里的两条"依赖链"：

- `hug`（第 4 条）依赖 `ug`（第 2 条）先存在——没有 `ug`，就拼不出 `hug`；
- `hugs`（第 9 条）又依赖 `hug`（第 4 条）先存在。

也就是说：**先学到的规则优先级更高，而且后面的规则往往站在前面规则的肩膀上。**

#### 第二步：动手走一遍编码流程

输入文本 `"hugs"`。编码方法一句话：**预分词之后，对每个词从头到尾逐条扫描规则表，能合并就合并；扫完一遍如果还有可合并的，就再扫一遍，直到没有规则能匹配。**

对着规则表走一遍：

| 步骤 | 当前符号序列 | 扫描到哪条规则 | 发生了什么 |
| --- | --- | --- | --- |
| 0 | `[h, u, g, s]` | — | 预分词得到单词 `hugs`，拆成字符 |
| 1 | `[h, u, g, s]` | 第 1 条 `(p,u)` | 没有相邻的 p 和 u，跳过 |
| 2 | `[h, u, g, s]` | 第 2 条 `(u,g)` | **命中**，合并 → `[h, ug, s]` |
| 3 | `[h, ug, s]` | 第 3 条 `(pu,n)` | 不匹配，跳过 |
| 4 | `[h, ug, s]` | 第 4 条 `(h,ug)` | **命中**，合并 → `[hug, s]` |
| 5 | `[hug, s]` | 第 5 ~ 8 条 | 都不匹配，跳过 |
| 6 | `[hug, s]` | 第 9 条 `(hug,s)` | **命中**，合并 → `[hugs]` |
| 7 | `[hugs]` | 第 10 条 `(g,s)` | `[hugs]` 里已经没有独立的 g 和 s，跳过 |
| 8 | `[hugs]` | 全部扫完 | 没有规则可应用，结束 |

查词表：`hugs` → ID `16`。编码结果是 `[16]`——4 个字符的单词，最后只剩 1 个 Token。

再切一个 `"pugs"`：

| 步骤 | 当前序列 | 扫描到的规则 | 结果 |
| --- | --- | --- | --- |
| 1 | `[p, u, g, s]` | 第 1 条 `(p,u)` | 命中 → `[pu, g, s]` |
| 2 | `[pu, g, s]` | 第 2 条 `(u,g)` | u 已经被并进 `pu`，这条规则**失效**，跳过 |
| 3 | `[pu, g, s]` | 第 5 条 `(pu,g)` | 命中 → `[pug, s]` |
| 4 | `[pug, s]` | 剩余规则 | 没有 `(pug,s)` 这条规则，结束 |

查词表得 `[12, 6]`。注意：`hugs` 是 1 个 Token，`pugs` 是 2 个——不是规则"偏心"，而是训练语料里 `hug s` 出现 3 次、`pug s` 只出现 2 次，`(hug,s)` 先学到；10 轮名额用完时，还轮不到 `(pug,s)`。

**这一步的关键观察**：在初始序列 `[p, u, g, s]` 上，第 1 条 `(p,u)` 和第 2 条 `(u,g)` 是**同时可用**的。谁先执行？排在前面的 `(p,u)`。而它一旦执行，`u` 被包进 `pu`，`(u,g)` 就永远失去了在 `pugs` 上生效的机会。所以优先级不只是"谁先谁后"——**先执行哪条，还会改变后面哪些规则能用、最终拼出什么**。这就是切分结果不同的根源。

#### 第三步：为什么同样一句话会切出不同子词

**原因一：规则表不同。** 规则表是训练语料"喂"出来的，换个语料，频率分布就变，学到的规则和顺序都跟着变。

比如另一个模型只学了 2 条规则：`(h,u) → hu`、`(g,s) → gs`。同样切 `"hugs"`：

```text
[h, u, g, s] → 规则(h,u) → [hu, g, s] → 规则(g,s) → [hu, gs]
```

结果是 `[hu, gs]`，和 `[hugs]` 完全不同——可输入的 4 个字符一模一样。

**原因二：合并轮数不同。** 同一份语料，提前叫停（词表小）和学满 10 轮（词表大），切分粒度完全不同：

| 模型 | 规则条数 | `"hugs"` 的切分 |
| --- | --- | --- |
| 模型甲 | 0 条（纯字符级） | `[h, u, g, s]` |
| 模型乙 | 2 条 | `[h, ug, s]` |
| 模型丙 | 4 条 | `[hug, s]` |
| 模型丁 | 10 条 | `[hugs]` |

**原因三：规则顺序不同。** 即使两张规则表内容相同，只要顺序不同，切分也可能不同。假设某张表把 `(u,g)` 排在第 1 条、`(p,u)` 排在第 2 条，且没有 `(p,ug)` 规则，切 `"pugs"`：

```text
[p, u, g, s] → 先应用(u,g) → [p, ug, s] → 再试(p,u) → 不匹配（u 已并入 ug）→ 停在 [p, ug, s]
```

而按原表顺序切出来是 `[pug, s]`。**同样的规则、不同的顺序，切出不同的子词。**

结论：**切分结果 = 文本 + 预分词规则 + 合并规则表（内容和顺序）。** 三者缺一不可，这就是 GPT-2、BERT、LLaMA 的分词器不能混用的原因。

#### 第四步：再走一遍解码流程

解码是编码的逆操作：**拿 Token ID 查词表得到字符串，按顺序拼接，最后还原词边界标记。**

模型丁收到 `[12, 6]`，走一遍：

| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 1 | ID 12 查词表 | `pug` |
| 2 | ID 6 查词表 | `s` |
| 3 | 拼接 | `pugs` |
| 4 | 还原边界标记 | 没有 `Ġ`，不加空格 |

文本 `pugs` 被完整还原，一个字符都没丢。

那空格去哪了？回到第 3 节：GPT-2 的预分词把**前导空格留在词内部**，词表里存的是 `Ġworld` 这样的 Token。所以 `"new world"` 编码后大致是 `[Ġnew, Ġworld]`，解码时把 `Ġ` 换成空格即可。如果没有这套边界标记，解码后相邻单词会粘在一起——这不是 bug，是设计：**空格信息必须由某个 Token 背着走。**

#### 常见坑（避坑清单）

1. **拿 A 模型的 ID 去 B 模型查表**：模型甲里 ID 16 是 `hugs`，模型乙里 ID 16 可能是 `cat`。ID 只在自家词表内有意义，混用解出来的东西毫无意义。
2. **以为同一句话切分唯一**：换模型、换词表大小、甚至只换预分词规则，切分结果都不同。写代码时永远不要假设"这个词一定是 1 个 Token"。
3. **用字符数估算 Token 数**：`hugs` 是 4 个字符，却只占 1 个 Token。估算上下文长度要按 Token 算，不能按字符数或单词数。
4. **手动调整规则顺序**：合并顺序是模型的一部分。自己重排规则表，等于造了一个新模型，和原模型不再兼容。
5. **特殊 Token 被切碎**：`<|endoftext|>` 这类 Token 若不保护，会被切成 `<`、`|`、`end` 等碎片，控制指令直接失效。
6. **以为 BPE 会跨词合并**：`"new"` 和 `"est"` 相邻时不会被并成 `newest`——预分词在训练和推理时都挡在前面。

#### 自测练习（附答案）

**练习 1**：用第一步的 10 条规则，分别切分 `punk` 和 `buns`。

答案：

- `punk`：`[p,u,n,k]` → 第 1 条 `(p,u)` → `[pu,n,k]` → 第 3 条 `(pu,n)` → `[pun,k]` → 第 8 条 `(pun,k)` → `[punk]`，即 ID `[15]`
- `buns`：`[b,u,n,s]` → 第 6 条 `(b,u)` → `[bu,n,s]` → 第 7 条 `(bu,n)` → `[bun,s]` → 第 9、10 条都不匹配 → `[bun, s]`，即 ID `[14, 6]`

**练习 2**：判断对错——"两个模型词表内容完全相同，切分结果就一定相同。"

答案：错。规则表的**顺序**不同，切分结果可能不同（见第三步原因三）。

**练习 3**：模型甲中 ID 16 = `hugs`，模型乙中 ID 16 = `cat`。把模型甲编码出的 `[16]` 直接交给模型乙解码，会得到什么？说明什么？

答案：得到 `cat`。说明 ID 没有跨模型的通用含义，编码和解码必须使用同一个词表。

**练习 4**：`hugs` 能并成 1 个 Token，`pugs` 为什么不行？

答案：训练语料中 `hug s` 出现 3 次、`pug s` 只出现 2 次，`(hug,s)` 排在第 9 条先学到；10 轮合并结束时还没轮到 `(pug,s)`。频率和优先级共同决定了这个不对称的结果。

## 5. 特殊 Token 的类型与用途

### 5.1 什么是特殊 Token

特殊 Token（Special Tokens）是**人工定义、不通过 BPE 合并产生**的固定 Token。它们被直接追加到词表中，拥有独立 ID，在分词时**原样匹配输出**，不可再拆分为子词。

### 5.2 常见类型一览

| 类型 | 常见形式 | 用途 |
| --- | --- | --- |
| 未知词 | `<unk>`、`[UNK]` | 词表外字符的兜底占位（byte-level BPE 下基本用不到） |
| 填充 | `<pad>`、`[PAD]` | 对齐 batch 内序列长度，通常不参与损失计算 |
| 序列开始 / 结束 | `<s>` / `</s>`、`<bos>` / `<eos>`、`[CLS]` / `[SEP]` | 标记文本边界，帮助模型识别序列起止 |
| 掩码 | `[MASK]` | BERT 预训练 MLM 任务中标记被遮盖的位置 |
| 文档分隔 | `<|endoftext|>` | GPT-2 中分隔多个相互独立的文档 |
| 对话结构标记 | `<|user|>`、`<|assistant|>`、`<|system|>` | ChatML 等对话模板中标记角色边界 |
| 功能标记 | `<|tool_call|>`、`<|fim_prefix|>` 等 | 工具调用、代码填充（FIM）等特殊任务 |

### 5.3 使用注意事项

1. **原子性**：特殊 Token 不参与 BPE 合并，训练与分词时都作为不可拆分的整体。
2. **词表位置**：通常追加在 BPE 词表之后，分配连续的 ID。
3. **匹配优先级**：分词时特殊 Token 优先匹配（一般是最长匹配），防止被切碎成普通子词。
4. **训练时保护**：训练语料中若出现特殊 Token 字符串，需先剔除或替换为占位符，否则其中的字符（如 `<`、`|`）会污染合并统计。
5. **兼容性**：模型迁移、微调、量化部署时，特殊 Token 的集合与 ID 必须保持一致，否则行为错乱。

## 6. BPE 训练处理逻辑分析

### 6.1 合并策略

1. **贪心全局策略**：每一轮扫描全量统计，选择当前频率最高的**一对**符号合并，一次只新增一个词表项。这保证了规则表的确定性，也让训练过程可随时中止（得到前 k 条规则就是前 k 轮的词表）。
2. **频率并列（tie）的处理**：多个符号对频率相同时，实现必须定义**确定性的 tie-break 规则**（如按符号对字符串的字典序，或按首次出现的顺序），否则同一份语料在不同机器/实现上可能得到不同的词表。GPT-2 与 sentencepiece 的具体 tie-break 规则并不相同，两套合并规则表不可混用。
3. **规则有序性**：合并规则按学习顺序排列，编码时必须按此顺序应用。先学到的规则优先级更高，这与训练时"从高频到低频"的贪心过程保持一致。
4. **与最优化的关系**：贪心策略不保证全局最优压缩率，但实现简单、训练高效，且实际语言建模效果与更复杂的算法（如 Unigram）相当。

### 6.2 频率统计

1. **词级聚合计数**：预分词后，先统计每个"词"在语料中的出现频率，再对每个词统计内部相邻符号对的出现次数，最后按词频加权累加得到全局计数：

   ```text
   count(符号对 x) = Σ_w  freq(w) × count_in_word(x, w)
   ```

   这样避免逐字节重复扫描全文，长文本语料也能高效统计。

2. **增量更新**：某一轮合并只会影响**包含被合并对**的那些词，其他词的计数不变。工程实现通常只重算受影响的词，而不是每轮全量重扫（详见 6.4）。

3. **最小频率阈值**：可设置最小合并频率（如 `min_frequency`），低于阈值的符号对不参与合并，避免罕见组合浪费词表空间；未达标的词保持更细粒度的切分。

4. **跨词不计数**：统计只发生在词内部，预分词天然地隔断了跨词符号对，这是统计口径正确性的前提。

### 6.3 边界情况处理

| 边界情况 | 处理方式 |
| --- | --- |
| **跨词合并** | 由预分词阻止；合并永不跨词边界，空格/标点通过 `Ġ`（前导空格）或 `</w>`（词尾标记）保留在词内 |
| **未登录字符（OOV）** | 字符级词表下映射为 `<unk>`；byte-level BPE 以 256 个字节值为初始词表，任何 UTF-8 字节序列都可编码，从根本上消除 OOV |
| **特殊 Token 混入语料** | 训练前剔除或替换为占位符，防止其字符（如 `<`、`\|`）参与合并统计 |
| **标点、空白、数字** | 由预分词正则分组处理：GPT-2 将连续字母、连续数字、连续标点、连续空白分别成组，数字逐位拆分或按块拆分取决于预分词规则 |
| **重复出现位置** | 合并是**全局替换**：同一符号对在所有词中的所有出现位置一次性合并，保证规则应用的一致性 |
| **词表达到上限** | 达到 `vocab_size`（或 `num_merges`）即停止训练；未合并完的罕见词保持较细粒度切分，不影响正确性 |
| **Unicode 多形态** | 可选 Unicode 归一化（NFC/NFKC），把同一字符的不同编码形式统一为同一符号后再训练 |
| **极小语料 / 单字词** | 没有可合并对时训练自然终止，分词退化为字符级切分，算法依然成立 |

### 6.4 训练复杂度与工程优化

- **朴素实现**：每轮需要扫描全语料统计符号对，复杂度约为 `O(N)`，共 M 轮合并，总复杂度 `O(M × N)`（N 为语料规模，M 为合并次数，通常 1k ~ 50k）。
- **增量统计**：合并后只重算包含被合并对的词，大幅减少重复扫描。
- **倒排索引**：维护"符号对 → 出现位置（词，下标）"的索引，快速定位所有需要重算的词。
- **优先队列 / 堆**：用堆维护各符号对的计数，快速取出当前最高频对。
- **代表实现**：`sentencepiece`（C++）、HuggingFace `tokenizers`（Rust）、`tiktoken`（Rust）等，均采用上述优化，可在分钟级完成数十亿词级别的训练。

## 7. 小结

1. **Tokenizer** 是文本与模型之间的桥梁，负责"文本 ↔ Token ID"的双向映射；子词分词在序列长度、词表规模与语义粒度之间取得平衡，BPE 是其中最主流的算法。
2. **BPE** 从字符（或字节）出发，迭代合并语料中频率最高的相邻符号对，训练产物是一张**有序合并规则表**；它无监督、高效、可控词表大小，并天然缓解 OOV 问题。
3. **预分词**在训练前把文本切成词级别的块，限定合并不跨词边界，保留空格/标点结构，直接决定统计口径与最终切分行为。
4. **训练流程**四步循环：构建初始词表 → 统计相邻符号对频率（按词频加权）→ 合并全局最高频对 → 更新词表并迭代，直至达到词表上限。
5. **特殊 Token**（`<pad>`、`<eos>`、`<|endoftext|>` 等）人工追加、原子不可分，用于填充、边界标记、对话结构等控制目的，训练时需保护，部署时需保证一致。
6. **处理逻辑**上，BPE 采用贪心全局合并 + 确定性 tie-break；频率统计以词为单位聚合并支持增量更新；边界情况（OOV、跨词、特殊 Token、词表上限等）均有明确的工程处理范式。

掌握 BPE 的原理，是理解 GPT、LLaMA 等大语言模型"如何阅读文本"的第一步，也为进一步学习 WordPiece、Unigram、tiktoken 等分词方案打下基础。
