## 1. 一张图看懂端到端流程

### 1.1 训练和推理，是两条相反的路

```text
【训练】有标准答案，批量改作业

token 文件
   │  memmap + DataLoader
   ▼
x, y: (B, T)
   │  模型 forward
   ▼
logits: (B, T, V)
   │  cross entropy（和 y 比较）
   ▼
loss: 标量
   │  backward
   ▼
梯度
   │  裁剪 + AdamW
   ▼
更新后的参数
   │  定期保存
   ▼
checkpoint
```

```text
【推理】没有标准答案，自己往下写

prompt 文本
   │  tokenizer
   ▼
token IDs: (1, T)
   │  模型 forward
   ▼
logits: (1, T, V)
   │  只取最后一个位置
   ▼
下一个 token 的概率分布: (1, V)
   │  温度缩放 + top-p 采样
   ▼
下一个 token
   │  拼到序列末尾
   └──────────────► 回到 forward，继续生成
```

### 1.2 一句话对比

| 维度 | 训练 | 推理 |
| --- | --- | --- |
| 有没有标准答案 | 有，`y` 就是下一个 token | 没有，模型自己采样 |
| 一次处理多少位置 | 一次算 `B*T` 个位置 | 一次只关心最后一个位置 |
| 是否并行 | 可以，整段序列并行 | 串行，生成一个接一个 |
| 是否算梯度 | 是，需要 `backward` | 否，`torch.no_grad()` |
| 模型模式 | `model.train()` | `model.eval()` |
| 输出 | loss、梯度 | token ID 序列 |
| 典型耗时 | 受限于算力和显存 | 受限于串行步数和上下文长度 |

### 1.3 比喻

- **训练**像老师批改作业：学生（模型）先写答案，老师（损失函数）拿标准答案对照，指出差距，学生调整。
- **推理**像学生自己写作文：没有标准答案，写一个字，读一遍前文，再写下一个字。
- **checkpoint**像存档：训练中途保存，机器挂了可以继续。
- **上下文窗口**像书桌大小：一次只能摊开固定数量的卡片，写太长就要把旧卡片收起来。

## 2. 训练流程：老师批改作业

### 2.1 第一步：准备数据

`main_train.py` 用 `np.memmap` 打开训练集和验证集：

```python
train_data = np.memmap(args.train_data_path, dtype=np.uint16, mode="r")
val_data = np.memmap(args.valid_data_path, dtype=np.uint16, mode="r")
```

要点：

- 文件是**裸二进制 token 流**，不是 `.npy`；
- `dtype` 必须和写文件时一致，通常是 `uint16`；
- `memmap` 不会把整个文件读进内存；
- `DataLoader` 负责切出 `x, y`，形状都是 `(B, T)`。

> 数据加载的细节见 `Data Loader.md`。这里只需要记住：`x` 是输入，`y` 是右移一位的标签。

### 2.2 第二步：搭模型

`main_train.py` 自己组装了一个 `TransformerLM`：

```text
idx (B,T)
  -> token embedding
  -> N × TransformerBlock
       -> RMSNorm -> 因果多头注意力 -> 残差
       -> RMSNorm -> SwiGLU FFN -> 残差
  -> final RMSNorm
  -> lm_head
  -> logits (B,T,V)
```

为什么不用 `Transformer_LM.py` 里的模型？

`main_train.py` 开头写得很清楚：

> `Transformer_LM.py` 是“用外部 state_dict 前向”的写法，权重挂在普通属性上，加载过程是 detach 的；`model.parameters()` 为空，梯度拿不到，`optimizer.step()` 什么也不会改。

所以训练版把同样的零件重新组织成所有参数都是 `nn.Parameter` 的 `nn.Module`。

> 这是一个很实际的工程坑：**能对拍前向，不等于能训练。** 训练要求参数被注册进优化器，并且梯度能回传。

### 2.3 第三步：一个训练 step

`main_train.py` 的主循环可以压缩成 9 步：

```python
# 1. 计算这一步的学习率
lr = schedule(it)
for group in optimizer.param_groups:
    group["lr"] = lr

# 2. 切换到训练模式
model.train()

# 3. 取一个 batch
x, y = train_loader.get_train_batch_data()   # (B,T), (B,T)
x, y = x.to(device), y.to(device)

# 4. 前向
logits = model(x)                            # (B,T,V)

# 5. 算损失（内部已经是批平均，不用再除 B*T）
loss = CrossEntropyLoss(
    logits.reshape(-1, vocab_size),
    y.reshape(-1),
).forward()

# 6. 清空旧梯度
optimizer.zero_grad()

# 7. 反向传播
loss.backward()

# 8. 梯度裁剪
clamp()

# 9. 更新参数
optimizer.step()
```

下面逐步解释。

### 2.4 学习率：先 warmup，再余弦下降

`CosineSchedule` 根据 `iteration` 返回学习率：

```python
lr = schedule(it)
for group in optimizer.param_groups:
    group["lr"] = lr
```

为什么每一步都要重新写 `lr`？

- `optimizer.state_dict()` 里的 `param_groups` 也包含 `lr`；
- 如果不主动覆盖，恢复 checkpoint 后可能用回旧学习率；
- 调度器是“纯函数”，它不会自己改优化器，调用方要负责写回。

> 学习率细节见 `学习率调度：Cosine Schedule.md`。

### 2.5 前向：一次算 T 个位置

```python
logits = model(x)   # (B,T,V)
```

模型对每个位置都输出一个词表分布：

```text
位置 0 的 logits -> 预测 y[0,0]
位置 1 的 logits -> 预测 y[0,1]
...
```

因为有 causal mask，位置 `t` 只能看到 `0..t`，不会偷看未来。

### 2.6 损失：为什么是“平均”而不是“求和”

`CrossEntropyLoss` 内部做两件事：

```python
log_probs = log_softmax(inputs, dim=1)              # (B*T, V)
log_p = log_probs[range(B*T), targets]              # (B*T,)
return -log_p.mean()                                # 标量
```

先把 `(B, T, V)` 拉平成 `(B*T, V)`——模型给每个位置各出一个词表分布，
损失要按位置平均，所以 `B*T` 个位置一起进。

**用 mean 而不是 sum**：

- 求和会让 loss 随 batch 大小线性放大，梯度也跟着放大，等效于偷偷把学习率乘了 `B*T`；
- 平均值下 loss 和 PPL 的数值不随 batch 漂移，不同配置的曲线才能直接比较；
- 讲义和 `test_cross_entropy` 对标的就是 `F.cross_entropy` 的默认 `reduction="mean"`。

`main_train.py` 直接拿来用，不再做任何缩放：

```python
loss = CrossEntropyLoss(
    logits.reshape(-1, vocab_size),
    y.reshape(-1),
).forward()
```

> 早先的实现返回的是求和，调用方得自己 `/ (B*T)`。那种写法容易漏，
> 一旦漏了就是“loss 看着不降、其实梯度大了几十倍”，现在统一收敛到类内部。

> 交叉熵细节见 `Cross_Entropy_Loss.md`。

### 2.7 清梯度、反向、裁剪、更新

顺序很重要：

```python
optimizer.zero_grad()
loss.backward()
clamp()
optimizer.step()
```

| 步骤 | 作用 | 如果做错 |
| --- | --- | --- |
| `zero_grad()` | 清空上一步梯度 | 梯度跨 batch 累加，更新越来越大 |
| `backward()` | 计算梯度 | 没有梯度，参数不动 |
| `clamp()` | 全局 L2 范数裁剪 | 梯度爆炸时可能一步毁掉模型 |
| `step()` | 用梯度更新参数 | 参数不变 |

`GradientClip` 的做法是：

```text
把所有梯度拼成一根长向量
计算 L2 范数
如果超过 max_norm，就整体乘以 max_norm / norm
```

它只改变梯度的长度，不改变方向。

> 细节见 `Gradient Clipping.md`。

### 2.8 验证：固定一批，避免噪声

训练循环里每隔 `eval_every` 步验证一次：

```python
model.eval()
with torch.no_grad():
    v_logits = model(vx)
    v_loss = CrossEntropyLoss(
        v_logits.reshape(-1, vocab_size),
        vy.reshape(-1),
    ).forward() / (vx.shape[0] * vx.shape[1])
```

两个关键点：

1. **`model.eval()`**：关闭 dropout 等训练专用行为；
2. **`torch.no_grad()`**：不建计算图，省显存、加速。

`vx, vy` 是在训练开始前固定下来的一批验证数据。这样每次验证用的样本相同，`val_loss` 曲线不会因为采样不同而上下抖动。

### 2.9 保存 checkpoint

```python
if args.save_every > 0 and it % args.save_every == 0 and it > 0:
    save_checkpoint(model, optimizer, it + 1, ckpt_path)
```

保存的是：

- 模型权重；
- 优化器状态（AdamW 的 `m/v`、`step`、参数组）；
- 已完成步数 `it + 1`。

训练结束时还会保存一份 `ckpt_final.pt`，避免下次启动又把 `ckpt.pt` 当成“未完成”继续跑。

> 细节见 `CheckPoint.md`。

### 2.10 训练循环全景

```text
for it in range(start_iter, max_iters):
    ├── 计算 lr，写回 optimizer
    ├── model.train()
    ├── 取 batch x, y
    ├── forward -> logits
    ├── cross entropy -> loss
    ├── zero_grad
    ├── backward
    ├── clip
    ├── optimizer.step()
    ├── 每隔 eval_every：验证
    └── 每隔 save_every：保存
```

## 3. 推理流程：学生自己写作文

### 3.1 推理不是“再跑一次训练”

推理没有标签、没有损失、没有反向传播。它只做：

```text
给一段 prompt
  -> 预测下一个 token 的分布
  -> 采样一个 token
  -> 拼到 prompt 后面
  -> 重复
```

### 3.2 推理的五个步骤

#### 第一步：加载模型和 checkpoint

```python
model = TransformerLM(...)
checkpoint = torch.load("ckpt_final.pt", map_location="cpu", weights_only=False)
model.load_state_dict(checkpoint["model_state_dict"])
model.to(device)
model.eval()
```

推理只需要模型权重；优化器状态和 `iteration` 可以不用。

#### 第二步：tokenize prompt

```python
prompt_ids = tokenizer.encode("今天天气真")
input_tokens = torch.tensor(prompt_ids, device=device).unsqueeze(0)  # (1,T)
```

`Inference.py` 里的 `decode_token` 接受 `list[int]` 或任意形状的整数张量，内部统一整理成 `(1, T)`：

```python
ids = torch.as_tensor(input_tokens, dtype=torch.long).view(1, -1)
device = next(model.parameters()).device      # 读模型参数所在的设备
ids = ids.to(device)
```

两个要点：

- 用 `as_tensor` 而不是 `tensor`：传进来已经是张量时不会多拷一次；
- device 由函数自己从模型参数上读，调用方不用关心模型在 CPU 还是 GPU。

如果模型一个参数都没有（比如拿个假模型来测），`next(...)` 会抛 `StopIteration`，代码里捕获后回退到 CPU。

#### 第三步：前向，只取最后一个位置

```python
logits = model(input_tokens)          # (1,T,V)
last_logits = logits[:, -1, :]        # (1,V)
```

为什么只取最后一个？

- 前面的位置在训练时已经见过；
- 生成时我们只关心“当前序列的下一个 token”；
- 取 `logits[:, -1, :]` 才是对的，取错维度会得到 `(1,T)` 之类的错误形状。

#### 第四步：温度缩放 + top-p 采样

```python
probs = temperature_scaling(logits, temperature)   # (1,V)
next_token = top_p_sampling(probs, top_p)          # (1,1)
```

#### 第五步：拼接，继续循环

```python
input_tokens = torch.cat([input_tokens, next_token], dim=-1)  # (1,T+1)
```

然后回到第三步，直到：

- 生成到 `max_tokens_to_generate`；
- 或者遇到 EOS（结束符，`eos_token_id`）；
- 上下文窗口满不停止——`Inference.py` 改成滑动窗口，只把最近 `context_length` 个 token 喂给模型，生成可以一直继续。

### 3.3 推理循环的骨架

```python
model.eval()

input_tokens = torch.tensor(prompt_ids, device=device).unsqueeze(0)

with torch.no_grad():
    for _ in range(max_new_tokens):
        window = input_tokens[:, -context_length:]     # 滑动窗口
        logits = model(window)                         # (1,T,V)
        probs = temperature_scaling(logits, temperature)
        next_token = top_p_sampling(probs, top_p)
        input_tokens = torch.cat([input_tokens, next_token], dim=-1)
        if eos_token_id is not None and int(next_token.item()) == eos_token_id:
            break
```

> 这是骨架。`Inference.py` 另外还处理了：device 自动跟随、EOS 停止、上下文滑窗、以及 `train()`/`eval()` 状态的恢复，见 §4.5 和 §4.6。

### 3.4 推理时模型的形状

| 步骤 | 形状 | 说明 |
| --- | --- | --- |
| prompt | `(1,T)` | 一个 batch，一条序列 |
| logits | `(1,T,V)` | 每个位置一个词表分布 |
| 取最后位置 | `(1,V)` | 只保留当前预测 |
| softmax 后 | `(1,V)` | 概率分布 |
| 采样 | `(1,1)` | 一个 token ID |
| 拼接后 | `(1,T+1)` | 序列变长 |

### 3.5 推理为什么慢

`Inference.py` 没有实现 KV cache，所以每生成一个 token，都要把**整条序列**重新 forward 一遍：

```text
第 1 步：forward 长度 T
第 2 步：forward 长度 T+1
第 3 步：forward 长度 T+2
...
第 N 步：forward 长度 T+N-1
```

总计算量约：

$$
O(N \cdot T^2 \cdot d_{model})
$$

序列越长，每一步越慢。KV cache 的作用就是缓存历史 token 的 K/V，避免重复计算；本作业的推理实现是“朴素版”。

## 4. 自回归生成机制

### 4.1 一句话定义

**自回归（autoregressive）**：

> 用已经生成的内容，预测下一个 token；再把新 token 追加到内容里，继续预测。

数学上：

$$
p(x_1,x_2,\dots,x_N)
=
\prod_{t=1}^{N} p(x_t \mid x_1,\dots,x_{t-1})
$$

每一步只预测一个条件分布，然后采样一个 token，把它变成下一步的输入。

### 4.2 一个具体例子

假设 prompt 是：

```text
今天天气真
```

第一步：

```text
看到：今天天气真
预测：下一个 token 的概率分布
采样：好
序列变成：今天天气真好
```

第二步：

```text
看到：今天天气真好
预测：下一个 token 的概率分布
采样：适合
序列变成：今天天气真好适合
```

第三步：

```text
看到：今天天气真好适合
预测：下一个 token 的概率分布
采样：出去
序列变成：今天天气真好适合出去
```

依此类推。

### 4.3 训练时是“老师强迫”，推理时是“自己发挥”

| 阶段 | 输入 | 预测依据 |
| --- | --- | --- |
| 训练 | 完整真实序列 | 每个位置都看真实前缀（teacher forcing） |
| 推理 | 只有 prompt + 自己生成的 token | 自己生成的前缀 |

训练时因为 causal mask，模型可以在一次 forward 中并行计算所有位置；推理时必须串行，因为第 `t+1` 步依赖第 `t` 步采样出来的 token。

> 这也叫“曝光偏差”（exposure bias）：训练时模型总看正确前缀，推理时却要看自己可能犯错的前缀。采样策略和更大的模型可以缓解，但不能完全消除。

### 4.4 为什么不能一次生成整段

因为第 2 个 token 依赖第 1 个采样结果，第 3 个依赖前两个……每一步的输入都包含上一步的输出，所以必须串行。

训练时可以并行，是因为训练时所有真实 token 都已知，causal mask 保证每个位置只看前缀，不依赖模型自己的采样。

### 4.5 `Inference.py` 的生成循环

```python
def decode_token(input_tokens, model, max_tokens_to_generate, top_p=0.9,
                 temperature=1.0, eos_token_id=None, context_length=None):
    ids = torch.as_tensor(input_tokens, dtype=torch.long).view(1, -1)
    device = next(model.parameters()).device
    ids = ids.to(device)

    ctx = context_length or getattr(model, "context_length", None)
    was_training = model.training
    model.eval()

    try:
        with torch.no_grad():
            for _ in range(max_tokens_to_generate):
                window = ids if ctx is None else ids[:, -ctx:]     # 滑动窗口
                logits = model(window)
                probs = temperature_scaling(logits, temperature)
                next_token = top_p_sampling(probs, top_p)
                ids = torch.cat([ids, next_token], dim=-1)
                if eos_token_id is not None and int(next_token.item()) == eos_token_id:
                    break
    finally:
        model.train(was_training)          # 无论怎么退出都恢复原模式

    return ids
```

参数一览：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `input_tokens` | `list[int]` 或整数张量 | prompt，不能为空 |
| `max_tokens_to_generate` | int `>= 0` | 最多**新增**多少 token；`0` 表示原样返回 |
| `top_p` | `(0, 1]` | 核采样阈值 |
| `temperature` | `> 0` | 温度；`<= 0` 直接报错 |
| `eos_token_id` | int 或 None | 生成到它就停，并把它留在序列末尾 |
| `context_length` | int 或 None | 不传就从 `model.context_length` 读 |

### 4.6 这几个工程细节是怎么处理的

下面每一条都是曾经踩过的坑，现在都修好了。改动集中在 `Inference.py`，列出原因是为了以后别改回去。

| 问题 | 错误写法 | 现在的做法 |
| --- | --- | --- |
| 停止条件不生效 | `if input_tokens == "<endoftext>"` | 比较刚生成的 id：`if int(next_token.item()) == eos_token_id` |
| device 不匹配 | `torch.tensor(prompt)`，永远是 CPU | 从 `next(model.parameters()).device` 读设备再 `.to()` |
| 超出上下文窗口 | 不检查，`T` 一路涨到越界 | 只把 `ids[:, -ctx:]` 喂给模型，输出序列仍保留全部 |
| 模式不恢复 | `model.eval()` 之后再没切回 | `try/finally` 里 `model.train(was_training)` |

**关于停止条件**：`Tensor == "字符串"` 不会做逐元素比较，返回的是一个 Python `False`（实测），所以旧写法那个 `if` 永远不会进。改成比较 id 之后才真的能停。

**关于上下文**：这里选的是"滑动窗口"而不是"到点就停"——生成可以继续，只是模型看不到很早的内容。如果更在意回答完整性，也可以改成 `if ids.shape[1] >= ctx: break`。

**关于模式恢复**：在训练脚本里顺手调一次生成，模型会被永久留在 `eval` 状态（dropout 关掉），后续训练静默变差，而且不报错。`finally` 保证中途抛异常也能恢复。

还有一个没做的：**KV cache**。每步都重新 forward 整条序列，长文本会明显变慢。作业的朴素实现可以接受，工程上才需要加。

## 5. 训练与推理的核心逻辑对比

### 5.1 形状对比

| 阶段 | 输入 | 模型输出 | 取哪部分 | 后续 |
| --- | --- | --- | --- | --- |
| 训练 | `x:(B,T)` | `logits:(B,T,V)` | 全部位置 | 和 `y:(B,T)` 算交叉熵 |
| 推理 | `ids:(1,T)` | `logits:(1,T,V)` | 最后一个位置 `(1,V)` | softmax + 采样 |

### 5.2 损失 vs 采样

| 训练 | 推理 |
| --- | --- |
| 用 `logits` 和真实 `y` 算交叉熵 | 用 `logits[:, -1]` 算概率 |
| 目标是让正确 token 的概率变大 | 目标是从分布里抽一个 token |
| 需要梯度 | 不需要梯度 |
| 一次更新所有参数 | 一次只产出一个 token |

### 5.3 为什么训练不直接采样

训练需要**可微**的损失。采样（`multinomial`）是随机的、不可微的，不能直接拿来反向传播。所以训练用交叉熵，推理才用采样。

### 5.4 为什么推理不计算 loss

推理没有标签，也没有“正确答案”。它只需要根据当前分布生成下一个 token。

## 6. 上下文窗口限制

### 6.1 什么是上下文窗口

`context_length` 是模型一次最多能看的 token 数，也是位置编码（RoPE）支持的最大长度。

```text
context_length = 256
prompt 长度 = 200
最多还能生成 = 256 - 200 = 56 个 token
```

如果继续生成，序列长度变成 257，模型就会出问题。

### 6.2 超长会发生什么

`main_train.py` 的 `TransformerLM.forward` 有检查：

```python
if in_indices.shape[1] > self.context_length:
    raise ValueError(
        f"序列长度 {in_indices.shape[1]} 超过 context_length {self.context_length}"
    )
```

所以：

- 训练时 `DataLoader` 切出的 `T` 必须 `<= context_length`；
- 推理时 `prompt + 已生成` 必须 `<= context_length`；
- 否则会报错，或者 RoPE 位置表越界。

### 6.3 生成到上限怎么办

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 直接停止 | 到 `context_length` 就 break | 简单、安全 | 回答可能被截断 |
| 截断 prompt | 只保留最后 `context_length - max_new` 个 token | 能继续生成 | 丢失开头信息 |
| 滑动窗口 | 每次只喂最近 `context_length` 个 token | 可以无限生成 | 早期上下文丢失 |
| 扩大窗口 | 训练/位置编码支持更长 | 保留更多上下文 | 计算量按平方增长 |
| KV cache | 缓存历史 K/V | 加速，不改变窗口上限 | 仍需处理窗口 |

### 6.4 滑动窗口的直觉

上下文像一张书桌，只能摊开固定数量的卡片。写第 300 个字时，桌子放不下前面的所有卡片，只能把最旧的收起来，留下最近的。

```text
原始序列： [1, 2, 3, 4, 5, 6, 7, 8]
窗口 T=4：
  第 1 次看 [1,2,3,4]
  第 2 次看 [3,4,5,6]
  第 3 次看 [5,6,7,8]
```

缺点：模型看不到很早的信息，可能出现“前后矛盾”。

### 6.5 为什么不能只靠 KV cache

KV cache 解决的是“不要重复计算历史 K/V”，让每一步更快；它**不增加**模型能看的最大位置数。

窗口是“模型能看多远”，cache 是“看过的东西别重算”。两件事不一样。

## 7. 采样策略：温度缩放与 Top-p

### 7.1 贪心：每次都选最大概率

```python
next_token = logits.argmax(dim=-1)
```

优点：

- 确定性，容易复现；
- 不会抽到明显离谱的词。

缺点：

- 容易重复、原地打转；
- 同一段 prompt 永远生成同一句话；
- 缺乏多样性。

### 7.2 温度缩放：调节“性格”

公式：

$$
p_i = \operatorname{softmax}\left(\frac{z_i}{T}\right)
$$

其中 `z` 是 logits，`T` 是温度。

- `T < 1`：分布更尖，更保守，接近贪心；
- `T = 1`：原始分布；
- `T > 1`：分布更平，更随机，更容易跑题；
- `T = 0`：数学上除零，不能用；想要贪心请直接 `argmax`。

#### 一个具体例子

logits 是 `[2, 1, 0, -1]`：

| 温度 | 概率分布 |
| --- | --- |
| `T=0.5` | `[0.8650, 0.1171, 0.0158, 0.0021]` |
| `T=1.0` | `[0.6439, 0.2369, 0.0871, 0.0321]` |
| `T=2.0` | `[0.4551, 0.2760, 0.1674, 0.1015]` |

读法：

- 低温时，最高分 token 占 86.5%，几乎必选；
- 高温时，最高分只剩 45.5%，其他 token 也有机会。

#### 代码

`Inference.py`：

```python
def temperature_scaling(logits, temperature=1.0):
    if temperature <= 0:
        raise ValueError(f"temperature 必须 > 0，收到 {temperature}")
    if logits.dim() == 3:
        logits = logits[:, -1, :]      # (B,T,V) -> (B,V)
    return torch.softmax(logits / temperature, dim=-1)
```

注意：

- 输入可以是 `(B,T,V)`，也可以是已经取过最后位置的 `(B,V)`；
- `(B,T,V)` 时只取 `logits[:, -1, :]`，得到 `(B,V)`；
- 只有 3D 才切，这样两种形状都能用，调用方不用记着先切一刀；
- `temperature <= 0` 直接报错而不是算出 `inf/nan`——想要贪心请用 `argmax`。

上表那三行数字是实跑核对过的：`T=0.5 → [0.865, 0.1171, 0.0158, 0.0021]`，和上面的表格一致。

### 7.3 Top-p：只从“最有把握的一撮”里抽

#### 直觉

模型可能给 50000 个 token 都分配了非零概率。即使长尾概率很小，加起来也可能抽到奇怪的词。

Top-p（核采样，nucleus sampling）的做法：

> 把 token 按概率从大到小排好，只保留累积概率达到 `p` 的那一撮，再在这一撮里按比例抽。

比如 `p=0.9`：

```text
排序后概率：0.50, 0.30, 0.15, 0.05
累积概率：  0.50, 0.80, 0.95, 1.00
保留：      0.50, 0.30, 0.15（累积到 0.95，覆盖 90% 以上）
丢弃：      0.05
```

候选集大小是**自适应**的：

- 模型很确定时，候选集很小；
- 模型很犹豫时，候选集很大。

#### 算法步骤

```text
1. 对概率降序排序
2. 计算累积概率 cumsum
3. 只要"排在它前面的 token 累积还不够 p"，就保留它
4. 重新归一化
5. 用 multinomial 按概率抽一个
6. 用排序索引把"排名"翻译回原始 token id
```

第 3 步是讲义式 (24) 的定义：`V(p)` 是满足 `Σ q ≥ p` 的**最小**下标集合。降序排列后取"累积刚好达到 p"的那个前缀，就等于这个集合——包括那个让累积跨过阈值的 token。

#### 代码

`Inference.py` 的核心逻辑：

```python
sorted_probs, sorted_idx = torch.sort(probabilities, dim=-1, descending=True)
cumulative = torch.cumsum(sorted_probs, dim=-1)

# 前缀和（不含自己）< p 就保留：cumulative - p_i 就是第 i 个元素之前的累积
keep = (cumulative - sorted_probs) < top_p
filtered = sorted_probs.masked_fill(~keep, 0.0)

denom = filtered.sum(dim=-1, keepdim=True)
normalized = torch.where(denom > 0, filtered / denom.clamp_min(1e-12), fallback)

next_rank = torch.multinomial(normalized, 1)
next_token = torch.gather(sorted_idx, dim=-1, index=next_rank)
```

为什么用 `cumulative - sorted_probs` 而不是"先 cumsum 再 shift 一位"：第 `i` 个元素的前缀和就是 `cumsum[i] - p_i`，省一次拼接。第一个元素的前缀和恒为 0，所以只要 `top_p > 0` 它一定被保留——这同时保证了候选集非空。

#### 一个具体例子

概率 `[0.5, 0.3, 0.15, 0.05]`（实跑结果）：

| `top_p` | 保留的候选 | 覆盖概率 | 说明 |
| --- | --- | --- | --- |
| `1.0` | 全部 4 个 | 1.00 | 不截断，纯按分布采样 |
| `0.9` | `0.5, 0.3, 0.15` | 0.95 | 累积到 0.95 才 ≥ 0.9，第三个留下 |
| `0.8` | `0.5, 0.3` | 0.80 | 恰好等于 0.8，符合"≥ p 的最小集合" |
| `0.5` | `0.5` | 0.50 | 第一个就够 |
| `0.3` | `0.5` | 0.50 | p 比最大概率还小，仍保留一个 |
| `0.0` | `0.5` | 0.50 | 退化，走兜底取 argmax |

> 这里的保留规则和讲义式 (24) 一致，也和 Hugging Face 的 `top_p` 一致：**会保留那个让累积跨过阈值的 token**。早先的实现用的是 `cumsum > p`（连它一起砍），候选集比定义更小，`top_p` 偏小时还会把整行清零——现在两者都不会了。

#### 边界：`top_p` 太小

旧写法在 `top_p=0.3` 时会把整行清零，归一化 0/0 得到 NaN，`multinomial` 直接抛 `RuntimeError: probability tensor contains either inf, nan or element < 0`。

现在不会了：`keep` 的第一个元素恒为真，候选集至少有一个；即使人为传 `top_p <= 0` 让所有位都为假，代码也会走兜底分支：

```python
fallback = torch.zeros_like(filtered)
fallback[..., 0] = 1.0      # 退化成贪心
normalized = torch.where(denom > 0, filtered / denom.clamp_min(1e-12), fallback)
```

实测 `top_p=0.0` 返回概率最大的那个 token，不报错。

### 7.4 Top-k、Top-p、贪心的对比

| 策略 | 候选集 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 贪心 | 1 个 | 稳定、可复现 | 容易重复、无多样性 |
| Top-k | 固定 k 个 | 简单、候选数固定 | k 不随分布自适应 |
| Top-p | 累积概率到 p 的 token | 候选数自适应 | 实现细节多，太小会崩 |
| 纯采样 | 全部词表 | 多样性最高 | 容易抽到长尾怪词 |

### 7.5 推荐参数

没有“唯一正确”的参数，但可以作为起点：

| 场景 | temperature | top_p |
| --- | --- | --- |
| 事实问答、代码 | 0.2 ~ 0.7 | 0.8 ~ 0.95 |
| 通用对话 | 0.7 ~ 1.0 | 0.9 ~ 0.95 |
| 创意写作 | 1.0 ~ 1.3 | 0.9 ~ 1.0 |
| 需要完全可复现 | 贪心 / 固定种子 | 1.0 |

> 参数不是魔法。温度太高会胡说，太低会复读；top-p 太小会保守甚至崩，太大等于没截断。

### 7.6 顺序不能反

正确顺序：

```text
logits
  -> 除以 temperature
  -> softmax 得到 probs
  -> top-p 截断
  -> 重新归一化
  -> multinomial 采样
```

为什么不能先 top-p 再 softmax？

- top-p 的阈值是按概率刻度定义的；
- logits 没有归一化，累加没有意义；
- 必须先在概率空间里排序和累积。

6. 数据、模型、标签在同一 device；
7. 损失缩放正确（求和 vs 平均）。

`main_train.py` 开头专门解释了为什么不用 `Transformer_LM.py` 直接训练：那个版本适合对拍，不适合训练。

### 9.3 训练脚本与作业测试的关系

```text
作业测试：验证零件
  run_attention / run_swiglu / run_rmsnorm / run_transformer_lm ...

端到端训练：验证装配
  main_train.py
    -> DataLoader
    -> TransformerLM
    -> CrossEntropyLoss
    -> AdamW
    -> GradientClip
    -> CosineSchedule
    -> CheckPoint
```

建议顺序：

1. 先把各模块测试跑通；
2. 用小模型、小数据空跑 `main_train.py`；
3. 确认 loss 能下降；
4. 再扩大模型和数据；
5. 最后做推理生成。

### 9.4 一个“最小端到端”实验

```text
数据：几千个 token 的小文本
模型：d_model=64，num_layers=2，num_heads=4，context_length=64
训练：batch_size=4，max_iters=100
目标：loss 从随机水平明显下降
推理：prompt 长度为 10，生成 20 个 token
```

这个实验不追求效果，只验证：

- 数据能读；
- 前向形状对；
- loss 能反传；
- 参数会更新；
- checkpoint 能存能读；
- 生成循环不报错。

## 10. 常见问题 FAQ

### Q1：loss 为什么是平均，而不是总和？

总和对 batch 大小敏感：同一个模型，batch 翻倍 loss 就翻倍，梯度也翻倍，等效学习率被悄悄改了。平均之后不同 batch、不同配置的曲线才可比。`CrossEntropyLoss` 内部已经做了 `.mean()`，调用方不用再除 `B*T`。

### Q2：`zero_grad()` 应该放在 forward 前还是 backward 前？

都可以，只要在 `backward()` 之前清掉旧梯度即可。`main_train.py` 放在 forward 之后、backward 之前，逻辑更清楚。

### Q3：梯度裁剪为什么在 `step()` 之前？

裁剪的是梯度。`optimizer.step()` 一旦执行，参数已经更新，再裁梯度就晚了。

### Q4：推理为什么只取最后一个 logits？

因为前面的位置是历史 token，已经作为输入；当前要预测的是“序列末尾的下一个 token”，对应最后一个位置。

### Q5：推理为什么要 `model.eval()`？

关闭 dropout 等训练专用行为，保证输出稳定。`Inference.py` 在 `decode_token` 里调用了 `model.eval()`。

### Q6：推理为什么要 `torch.no_grad()`？

推理不需要梯度，关闭计算图可以省显存、加速。

### Q7：为什么生成会重复？

常见原因：

- 用了贪心，模型陷入重复循环；
- 温度太低；
- top-p 太小或太大；
- 训练数据/模型本身重复；
- 上下文窗口截断导致模型丢失前文。

可以尝试调高温度、调整 top-p，或加入重复惩罚（本仓库未实现）。

### Q8：temperature 和 top-p 先调哪个？

一般先固定 `top_p=0.9`，再调温度；或者先固定温度，再调 top-p。一次只改一个，才能判断变化来自哪里。

### Q9：temperature=0 可以吗？

不可以直接除。数学上是极限，代码里会除零得到 `inf/nan`。想要贪心请直接 `argmax`。

### Q10：top-p 和 top-k 有什么区别？

- top-k 固定保留 `k` 个候选；
- top-p 保留累积概率达到 `p` 的候选，候选数随分布自适应。

模型很确定时，top-p 会自动缩小候选集；top-k 不会。

### Q11：为什么生成到一定长度就报错？

因为超过了 `context_length`。`main_train.py` 的模型会显式抛 `ValueError`；其他 RoPE 实现可能位置越界。

解决：截断 prompt、滑动窗口、停止生成，或训练更长上下文。

### Q12：为什么推理没有用 KV cache？

`Inference.py` 是朴素实现，每步重算整条序列。这样代码简单，但长文本慢。KV cache 是工程优化，不改变模型数学。

### Q13：checkpoint 里的优化器状态推理时需要吗？

不需要。推理只加载模型权重；优化器状态是给“继续训练”用的。

### Q14：训练和推理可以共用一个 `forward` 吗？

可以。模型 forward 都返回 `logits`；区别在于：

- 训练取全部位置算 loss；
- 推理只取最后一个位置采样；
- 训练开梯度，推理关梯度；
- 训练 `train()`，推理 `eval()`。

### Q15：EOS 停止条件该怎么写？

比较**刚生成的那个 token id**，不是整条序列：

```python
ids = torch.cat([ids, next_token], dim=-1)
if eos_token_id is not None and int(next_token.item()) == eos_token_id:
    break
```

两个容易被写错的版本：

- `if ids == "<endoftext>"`：张量和字符串比较返回 Python `False`，条件永远不成立；
- `if next_token == eos_token_id`：这是逐元素比较，返回的是张量，放进 `if` 里在 batch=1 时能工作但语义含糊，`batch>1` 时直接抛 "Boolean value of Tensor is ambiguous"。

`Inference.py` 现在用的是 `.item()` 取出标量再比，明确且不会误判。注意 `eos_token_id` 要传 tokenizer 里 `<|endoftext|>` 对应的那个 **id**，传字符串是没用的。

### 11.1 自测清单

- [ ] 我知道 `CrossEntropyLoss` 内部返回批平均，不用再除 `B*T`；
- [ ] 我知道推理只取最后一个位置的 logits；
- [ ] 我能解释自回归生成为什么必须串行；
- [ ] 我知道 `context_length` 限制的是什么；
- [ ] 我能说出温度缩放和 top-p 的区别；
- [ ] 我知道 top-p 必须在 softmax 之后做；
- [ ] 我知道 `temperature=0` 不能直接用；
- [ ] 我知道 EOS 停止条件为什么要比较 token id 而不是整条序列；
- [ ] 我知道 `top_p` 的候选集是"累积刚好达到 p 的最小前缀"，不是"严格小于 p"；
- [ ] 我能用一个小模型空跑训练和生成。

### 11.2 一页速查

```text
【训练】
data -> x,y (B,T)
logits = model(x)                 # (B,T,V)
loss = CE(logits.reshape(-1,V), y.reshape(-1))    # 内部已是 mean
optimizer.zero_grad()
loss.backward()
clip()
optimizer.step()

【推理】
prompt -> (1,T)
loop:
    logits = model(ids)           # (1,T,V)
    probs = softmax(logits[:,-1,:] / temperature)
    next = top_p_sample(probs)
    ids = cat([ids, next], dim=-1)

【自回归】
p(x1..xN) = ∏ p(xt | x< t)
训练：一次算 T 个位置（teacher forcing）
推理：一次生成 1 个 token（串行）

【上下文】
prompt_len + generated_len <= context_length
超了：截断 / 滑动窗口 / 停止 / 扩窗

【采样】
greedy: argmax
temperature: softmax(z/T)
top-p: 累积概率到 p 的候选，重新归一化后采样

【常见坑】
- loss 多除/少除了一次 B*T（类内部已经平均过）
- zero_grad 忘记 / 位置错
- clip 放在 step 之后
- 推理忘记 eval / no_grad
- 推理输入没搬到模型 device
- 生成超过 context_length
- top-p 输入了 logits 而不是 probs
- 停止条件比较整个张量而不是新 token
```

### 11.3 一句话总结

> **训练是“看标准答案、批量改参数”，推理是“没有答案、一个 token 一个 token 地往下写”；两者共用同一个模型，但一个算 loss，一个做采样。**
